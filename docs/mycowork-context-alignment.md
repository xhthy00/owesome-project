# 对话上下文与 my-cowork 对齐

对照本地 `my-cowork/backend/cowork_harness/{service,agent_factory}.py` 和
`my-cowork/backend/model_integrations/context.py`，以实际代码为准。

| 能力 | 本项目实现 |
| --- | --- |
| 多轮消息 | 同一工作空间、用户、数据源、会话复用一个 PostgreSQL checkpoint；新一轮仅追加 `HumanMessage`，保留助手回复、工具调用和工具结果的配对关系。 |
| 首次导入历史 | 仅在 checkpoint 为空时导入宿主历史，最多 16 条消息、每条 8,000 字符；已有 checkpoint 时不重复注入。只导入带当前授权和发布版本指纹的记录。 |
| 系统提示 | 每轮重新构造当前授权范围与发布目录；续问继承确认的条件，用户最新修改覆盖历史条件。 |
| 自动压缩 | 直接使用锁定版本 DeepAgents 自带的 summarization middleware，不另建摘要循环，不按轮删除消息。SDK 使用模型 `profile.max_input_tokens`，默认 85% 触发，保留最近 10% 上下文。 |
| 未知容量 | SDK 未提供窗口大小时沿用官方保守默认值（170,000 tokens 触发，保留最近 6 条消息），界面显示容量未知，不以输出上限或本轮预算冒充容量。 |
| MiniMax | SDK profile 优先；仅原生 `api.minimax.io`、`api.minimaxi.com` 端点补齐 my-cowork 的同名模型容量表。自定义端点不推断容量。 |
| 历史归档 | 由官方 StateBackend 保存归档与大工具结果，并随 checkpoint 持久化；`read_file` 只允许读取 `/conversation_history/`、`/large_tool_results/`，支持压缩后按需取回细节。 |
| 当前占用 | 每次主模型请求完成后上报输入 token 数；厂商未返回用量时估算并标记 `context_estimated`。摘要和子图调用不覆盖主模型当前占用。 |
| 累计消耗 | 独立累计所有真实模型调用的输入、输出与总 token，包括内部摘要调用；回调为唯一来源，避免流式分片与完整消息重复计数。 |
| 澄清与计划 | `Command(resume=...)` 恢复原图；新一轮清空计划，保留消息；继续使用现有调用预算和中断标识校验。 |
| 展示与刷新 | `usage` SSE 新增 `context_tokens/context_limit/context_model/context_key/context_estimated`；累计消耗独立展示。上下文指标随记录 `exec_result.context_usage` 保存，刷新后恢复。 |
| 内部输出 | 摘要模型的正文不进入答案和思考流；只有主图 `model` 节点的输出参与最终答复。 |

本项目保留的宿主边界：

- 查询仍通过 DataSemantic 与已有行列权限执行，业务数值仍须由本轮查询验证。
- 权限规则、白名单、用户变量、角色豁免、教育范围、隐私模式、语义发布版本或绑定变化时，清空旧 checkpoint（含摘要与归档）。旧中断回复返回失效提示。
- 不带边界指纹的旧 checkpoint 在首次访问时重新开始；旧展示记录保留，但不作为已授权的模型历史自动导入。
- 虚拟归档只读能力用于上下文恢复，不开放宿主文件系统、shell 或任务委派。

验证覆盖：跨模型实例的多轮恢复、一次性导入历史、工具结果保留、权限及发布变化失效、真实官方压缩与归档、内部摘要不外泄、SDK 容量优先级、缺失用量估算、主模型占用与累计消耗分离，以及前端 SSE 和容量展示。

## 2026-11-09：规划门禁误判修复

会话 1611 的失败记录 3129 显示耗时约 26 秒、工具执行为零。只读检查 checkpoint
中的三次原始模型响应后，确认每次都有合法 `write_todos`，同时附带
`describe_semantic_model`。原门禁要求整批只能包含规划/澄清工具，因额外的描述调用
删除了整条响应，连同有效计划一起丢弃；三次重试后误报模型无法发布规划。

现在保留有效规划，通过官方工具真正写入 todos；同批的其他工具返回“尚未执行，
等待规划成功后再调用”，避免并行执行绕过阶段顺序。真正缺少规划时，为每个未执行
调用补齐工具错误结果，并以系统消息给出重试指引；仍按三次上限停止。失败提示不再
把这种运行时错误归咎为模型不支持工具调用。回归覆盖混合描述/查询响应、纠正后继续
执行，以及持续缺少规划时不执行查询。

后续针对所有提问共用链路的完整整改、回归范围及既有失败清单见
[提问链路代码审计与整改](chat-runtime-audit.md)。
