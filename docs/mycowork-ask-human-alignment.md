# Ask Human 与 my-cowork 对齐

日期：2026-11-09。对照本机 `my-cowork` 的实际代码：

- `backend/runtime_contract/__init__.py`：`HumanQuestionInput`、`HumanQuestionField`。
- `backend/cowork_harness/agent_factory.py`：澄清指令和 `interaction_tools`。
- `backend/cowork_harness/service.py`：回复验证、事件与图恢复。
- `renderer/src/components/chat/HumanQuestionCard.tsx`：表单、跳过、自定义回答和历史摘要。

两边都是**应用定义的 `ask_human` 工具，调用 LangGraph 原生 `interrupt()`，由 DeepAgents 图执行并通过 `Command(resume=...)` 恢复**。它不是 DeepAgents 内置的同名表单工具，也不是 `interrupt_on` 的工具执行审批卡片。

本项目现已进一步为所有业务问数（含简单问数）接入独立的强制评估阶段，详见 [查询条件评估](question-assessment.md)。下方保留表单对齐及此前漏问的诊断背景。

## 已对齐行为

| 环节 | 本项目行为 |
| --- | --- |
| 工具参数 | `question` 为说明，`options` 兼容单个选择题，`fields` 合并多个问题。字段支持 `label`、`kind=single/multiple/text`、`options`、`required`、`placeholder`；`required` 默认 false。 |
| 参数兼容 | 与参考实现一样接收 XML 转换后的 `item` 包装、单字段对象、`question` 标签别名和 `{label: ...}` 选项。通过 Pydantic 校验后再中断。 |
| 提问原则 | 只有缺少影响执行的关键信息时追问；工具可查明的事实直接查询；偏好可选，必要问题合并一次询问；不编造业务候选项。只在当前入口提供该工具时注入表单指令。 |
| 挂起与恢复 | `interrupt({kind: "human", question, options, fields})`；提交后 `Command(resume={interrupt_id: {answer: 文本}})`，工具只把 answer 文本交回模型。继续同一会话图，保留原问题、工具结果及预算。 |
| React 表单 | 按项切换、单选/多选/文本、必填提示、自定义填写、选填跳过、上一项保留答案。选择选项不会立即提交。未提供选择项的字段降级为文本。 |
| 汇总回复 | 按 `1. 字段名：答案` 汇总；多选用 `；` 分隔。全部选填跳过时明确请助手依据已有信息继续并标记待确认项。 |
| 折叠和失败 | 折叠不卸载表单；发送期间隐藏并保留草稿，回复被拒绝或网络失败后可继续填写。提交中禁用操作，阻止重复提交。 |
| 生命周期 | 显式发送 `human.answered` / `human.cancelled`，与展示记录保存是否成功分离。失效 ID 会结束旧卡片；新问题结束原等待，随后可以继续普通对话。 |
| 历史 | 表单随 `exec_result` 保存，回复记录关联 `human_reply_to/human_answer`，换题记录保存 `human_cancelled_to`。刷新后显示已回复/已结束摘要；兼容旧 `retry` 和无生命周期元数据的历史，避免旧追问重新弹出。 |
| 旧数据 | 兼容只有 `question` 的工具参数、旧 `kind=ask_human` checkpoint 和原始字符串 resume；旧 `options` 与编号问题仍可展示。 |

## 保留的项目边界

- 继续使用现有 `/api/v1/chat/chat-stream` 和 `clarify` SSE，携带 `question_id/interrupt_id/fields/options/status`，不引入 my-cowork 的项目、任务或独立 `human-reply` REST 模型。
- 数据查询和授权仍由现有 DataSemantic、用户、工作空间、数据源、发布版本和会话边界校验。恢复时必须提供匹配的 ID；并发锁、过期 ID 和重复回复不会重复执行原工具。
- 每批只接受一个等待中的 `ask_human` 调用；多个字段放在同一个 `fields` 中。同批业务工具延后执行，避免追问和查询并发穿过等待边界。
- 必填校验位于表单；服务端验证回复非空、长度、ID 和授权。折叠表单后仍可用输入框直接补充文字。普通新问题上限 1000 字，多项澄清回复上限 8000 字。
- React 提供完整向导交互。保留的 Vue 客户端提供可读的字段/选项文本兼容，流式和刷新历史均保留问题内容，继续沿用原输入框回复。
- 执行状态以 checkpoint 为准，展示历史仍依赖问答记录保存。记录保存失败会显示错误步骤；若此时刷新，历史可能仍展示上一次等待记录，再次提交会被服务端作为已处理/失效追问结束，不会重放已执行的工具。

## 进一步改进：让追问始终可选

已经解除交互式会话中“先强制调用具名 write_todos，之后才能追问”的阶段限制：

- 需要规划时同时开放 `write_todos` 和 `ask_human`，使用 `auto` 让模型选择。无追问工具的入口仍沿用原网关兼容选择。
- 后端继续验证规划顺序；不能因为用了 `auto` 就在计划发布前执行业务查询。未遵守顺序的响应获得明确反馈，达到上限后停止。
- 即便进入阶段查询次数耗尽后的计划推进环节，`ask_human` 仍然可选；总调用/Token/图执行预算继续生效。
- 同批出现追问和规划、查询或其他工具时，只执行首个追问，其他操作返回未执行提示。用户回复后重新规划或查询，避免原批次中的假设直接生效。
- 提示词明确要求复用已确认条件；多个候选不能默认为已选定；不能擅自采用“最近一次”或某种统计口径，也不能把普通追问正文伪装成已挂起等待。

上述第一轮调整仅改变工具开放顺序。后续已接入独立评估，评估模型调用的成本、执行门禁与适用范围见 [查询条件评估](question-assessment.md)。

## 程序级歧义校验的后续设计

**已实现独立模型评估与执行门禁，尚未实现按业务契约进行的确定性歧义校验。** 当前运行链路没有接入“每种分析必需哪些条件、候选从哪里读取、允许单个/多个/最新等何种选择”的完整结构化契约。强制经过评估不能被表述为所有业务歧义都已百分之百识别。

建议在现有 DataSemantic 发布元数据上声明分析所需条件，而非在聊天代码中写死考试、学校或问题关键词：

1. **声明条件**：为分析能力声明必要条件、允许的选择方式、授权候选来源及唯一标识。按任务要求核验，避免每次都强制询问所有字段。
2. **查询候选**：通过现有权限链路查询真实候选，区分无记录、唯一记录、多个候选、分页/截断及查询失败。工具故障或没有数据不能被当成让用户任意挑选的歧义。
3. **程序裁决**：模型提出对象和条件，程序核实其证据与候选。未唯一确定且用户没有明确要求集合或最新时，阻止相应业务分析并调用原生中断；候选本身不代表选择已确认。
4. **确认后绑定**：用户选择绑定真实标识，写入 checkpoint；后续 SQL 校验必须保留已确认范围。续问复用条件，明确修改才重新解析；授权/发布版本变化后重新核验。

验收应覆盖：同名多批次必须澄清、明确“全部/最近一次”不重复追问、历史已确认不再询问、不可伪造候选或引用、候选变化及权限失效、SQL 不得扩大范围。通过这些检查后，才能把“应该追问”提升为已覆盖业务范围内的程序保证。

## 已核实的漏问案例：会话 1618

以下是接入强制评估前的历史记录诊断；现行入口已按 [查询条件评估](question-assessment.md) 调整。

2026-11-09 通过只读数据库事务核查截图对应的记录 3139：问题为“宝应地区本科达线率”，耗时 46,223 ms，9 次工具调用。该会话仅有这一问，没有用户历史确认的考试范围。

- 第 3 次调用查询考试候选，返回“2026届高三11月期中”“2026届高三1月期末”和“新华中学2027届高三10月月考”。
- 第 5 次调用查询区县达线指标，只限定宝应地区与本科线，没有限定考试；结果包含前两个考试。
- 后续继续汇总、查询全市对照并绘图；9 次调用中没有 `ask_human`，记录中也没有中断标识。
- 完整答复同时列出了11月期中和1月期末，截图显示的是表格上半部分。执行行为是默认展开所有有数据的批次，没有取得用户对考试范围的确认。
- 该问题被分类为简单问数，`_planning_required` 为 false；本次漏问发生在无需强制规划的路径。解除规划阶段对追问的限制，不能解决这一类漏问。
- 本机后端监听进程于15:34:19/20从当前项目目录启动，启用热更新；运行时源码最后修改时间为15:11:37，早于进程启动及本次请求。现有进程证据不支持“仍运行修改前旧进程”的解释。

本例体现的是尚未实现的业务范围校验：模型已看到多个候选，仍按所有可用批次继续分析，宿主没有强制拦截。期望行为是在确认宝应适用的候选后，让用户选择具体考试或明确选择两次对比，再进行业务分析。此处记录诊断事实，没有将增加提示词视为已经修复这类程序保证。
