# 所有问数共用的查询条件评估

日期：2026-11-09。

简单问数不需要步骤计划，但必须和复杂分析一样，先评估是否需要澄清。本机制在共用运行入口执行，不依赖地区、考试、问题关键词或某条特定提问的补丁。

## 执行顺序

1. 新一轮业务问题先运行独立的结构化评估，读取当前问题、用户历史、真实工具结果、授权范围和发布目录。
2. 返回 ready：条件足够，进入原有问数流程；简单问题直接查询，复杂问题发布计划。
3. 返回 lookup：仅开放读取字段、归档、真实候选和追问工具；探查后再次评估。
4. 返回 clarify：宿主在官方 before_model 钩子中生成 ask_human 调用并跳转到原生 tools 节点；LangGraph interrupt 暂停，前端展示表单。
5. 用户回复后，通过原有中断 ID 恢复，结合原问题与回复重新评估；只追问仍然缺少的必要项。

普通问候和已有白名单中的通用指标定义无需查询数据，使用明确的无需数据评估结果，不增加一次模型调用。

## 评估如何保持独立

- 评估器使用当前配置的问数模型，但拥有单独的任务指令及结构化输出协议，不沿用主模型“自己决定直接查”的路径。
- 上下文保留用户原话、工具调用与真实结果。主模型的解释和推测正文不作为评估依据，避免把它的假设当成用户确认。
- 数据模型的粒度、GROUP BY 或“可分列”不等于用户要求查询全部候选。先确认输入范围，再决定输出分组。
- 用户已确认的条件应复用；用户本轮修改优先。必要条件之外的偏好、可按发布口径直接分列/汇总的维度，不应被额外设为必选。
- 新读取的字段、归档、候选，以及后续 ask_human 回复会触发重评估。业务 query_semantic 中符合候选探查形态的 SELECT DISTINCT 结果也会触发重评估，避免发现多个候选后直接沿用最早的 ready。

## 执行门禁与失败处理

评估未放行时，模型工具列表中不开放业务查询、绘图和发布计划。宿主执行包装器还会检查同一状态，即便模型返回未绑定的业务工具调用，也只得到未执行结果。

lookup_question_context 是独立的候选探查工具：

- 只接受单条 SELECT DISTINCT，显式读取至多六个标识、名称或时间字段。
- 不允许聚合、窗口、写入、通配列、LIMIT/OFFSET，避免把“只取第一行”误认为候选唯一。
- 仍通过原有 DataSemantic 发布对象、行列权限、只读执行与结果截断限制。
- 每轮最多实际执行四次候选探查，包括同批并行调用；准备动作和反复探查同样有界。
- 候选不作为分析证据、统计结果或图表数据直接输出。
- generate-sql 继续保持不执行数据查询；需要候选数据时，应由调用方补充条件或改用带会话的交互入口。

输出结构无效时，只做一次有界格式修复；仍失败或输出截断时停止，不把失败默认当成 ready。服务错误和没有数据也不能成为编造候选的理由。

没有可恢复会话的执行入口收到 clarify 时，返回原有 clarification 描述并停止分析；不创建无法恢复的中断。

## 状态、展示和成本

- 评估状态随 checkpoint 保存；每条新问题重新评估，恢复原追问时保留原问题与状态。
- exec_result.question_assessment 保存决策、简短依据和评估轮次，执行记录显示“评估查询条件”；探查工具显示“确认分析范围”。
- 评估与格式修复使用相同的请求级调用/Token 预算。内部输出不会进入答案和思考流，累计用量包含真实评估调用；主模型当前上下文占用不被内部评估覆盖。
- 每条业务问题至少增加一次评估模型调用。需要探查或补充回复时会再次评估，因此存在额外延迟和 Token 消耗。图步骤余量已为评估节点增加，精确模型调用上限仍由原回调执行。
- 不增加新的模型服务、候选缓存数据库或人工回复 API，不改现有数据权限。

## 验证和边界

专项覆盖简单/复杂入口、对象/时间/考试/口径/比较基准、明确条件不强制追问、候选探查后重评估、无法绕过执行门禁、部分回复再次澄清、新一轮不沿用旧审批、无会话与 SQL 生成入口、格式失败、预算、并行探查限制、内部输出隔离和累计用量。

既有执行链路单元测试隔离评估器以测试执行本身；新增 test_question_assessment.py 使用真实评估解析与原生图、模拟模型响应验证完整流转。另用当前配置的真实模型和模拟数据、内存 checkpoint 验证多候选、明确指定、全部、唯一，以及由独立评估触发原生中断后恢复分析，未读取或写入业务数据库。

本轮后端专项197项、前端59项通过，修改 Python 文件 Ruff 与 git diff --check 通过。此前两项 React 类型检查错误及历史后端全量失败的范围见 [提问链路审计](chat-runtime-audit.md)。

保证的是“所有业务问数都必须经过评估，未放行不能执行业务分析”。评估的业务语义判断仍依赖模型，尚未变成按业务契约进行确定性候选绑定、验证每个 SQL 范围的系统；不能把这项机制表述成任意自然语言歧义都百分之百识别。
